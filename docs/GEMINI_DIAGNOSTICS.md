# Gemini failure diagnosis — 7 November 2026

## Offline request compatibility correction (latest)

Captured the exact request generated by installed google-genai 2.34.0 using a
fake key and HTTPX MockTransport. No network/provider request was made.
The request used POST `/v1beta/models/gemini-2.5-flash-lite:generateContent`,
with `contents`, `systemInstruction` and `generationConfig`. Temperature 0,
1800 output tokens, JSON MIME, 12-second timeout and one attempt were valid
SDK inputs; no tools, billing switches or unnecessary modalities were present.

**Confirmed defect:** Passing `Analysis` directly as legacy `response_schema`
serialized Pydantic's `extra='forbid'` as `additional_properties: false` at the
root and nested hypothesis object. That field is absent from the Developer API
legacy Schema definition. Google SDK issue
[1815](https://github.com/googleapis/python-genai/issues/1815) documents this exact
unsupported-field 400. The [API Schema reference](https://ai.google.dev/api/generate-content?hl=en)
distinguishes the legacy OpenAPI subset from the full JSON-schema input.
Public structured-output support for `additionalProperties` does not imply that
it is accepted inside legacy `responseSchema`.

**Small fix:** Generate a fresh schema from the existing Analysis model and remove
only `additionalProperties` from its object definitions before passing it to
legacy `response_schema`. Leave the model, API version, generation parameters,
field names, required fields, enums, string/array bounds and local model unchanged.
`Analysis.model_validate_json` still forbids extra properties and enforces all
bounds. Do not remove Pydantic `extra='forbid'` or relax response validation.

The old tests only verified that some schema was sent and returned a synthetic
success regardless of the request body; serialization success was incorrectly
treated as sufficient compatibility evidence. The stronger wire test failed on
the unsupported field before the correction and passed afterward. It now checks
the exact config shape, required fields, bounds/enums and nested object schemas.
Additional response tests reject root/nested extras, long strings, excessive
hypotheses and invalid confidence. Final offline run: **69 passed, 16 isolated-DB
tests skipped**, one existing upstream TestClient deprecation warning.

This definite request defect is a supported explanation for the observed 400,
but the historical raw Google response was not retained, so we cannot prove it
was the only issue affecting that call. A fresh explicitly approved live test is
still required. No new live request or quota reset was made. Deployment preparation
is unchanged; real-Gemini acceptance is still a release gate for a Gemini-enabled
demo, alongside the existing manual browser/public HTTPS checks.

## Failed requests and daily investigation quota

Keep current behavior: every reserved outbound investigation attempt consumes the
daily investigation allowance, including provider rejection, timeout and invalid
output. It is an attempt budget, not a count of successful analyses or provider
billing. A timed-out request may have reached Google; automatic refunds could
allow unlimited failed upstream calls and bypass the intended spend bound.

The global request allowance and cooldown still apply to rejected/repeated
analysis requests. Missing consent/key and cached/simulated results do not consume
a new external investigation. Pending reservations, row locks and the one-minute
failed-request guard remain unchanged. No counters were reset/refunded, no limits
raised, and no automatic retries added. The existing PostgreSQL tests cover failed
provider attempts and concurrent quota enforcement; rerunning them requires a
currently valid isolated test database, never the application endpoint.
